# v0.1 Persistence Spike Report (P-02)

**Status:** Akzeptanzkriterien in Chromium, fake-indexeddb und Microsoft Edge 154 (Windows) nachgewiesen<br>
**Datum:** 2026-09-27<br>
**Issue:** [#20 Local-first Persistenzarchitektur bewerten](https://github.com/WatzingerM21052/DnDimension/issues/20)<br>
**Entscheidung:** [DEC-009](../decisions/DEC-009-local-persistence-backup-and-cloud-evolution.md) wird bestätigt

## Ergebnis

IndexedDB über einen isolierten Dexie-Adapter erfüllt die Anforderungen aus DEC-009 und der v0.2-Spec: atomare Aggregate-Revisionen mit Audit-Event und Idempotenznachweis, erkennbare Revisionskonflikte zwischen Tabs, sichere Schema-Upgrades und ein wiederherstellbares Backup vor jeder Migration. Ein nativer IndexedDB-Fallback ist nicht nötig. OPFS bleibt großen, abgeleiteten Dateien vorbehalten und wurde nicht als Domain-Speicher untersucht.

## Koordination zwischen Tabs

Gewählt ist **optimistische Koordination**, keine Sperre und kein Leader-Tab:

1. Jeder Schreibvorgang trägt die erwartete Revision. Veraltete Commands bekommen `revision-conflict` mit der aktuellen Revision und ändern nichts.
2. Nach einem erfolgreichen Commit oder Restore sendet der Store über `BroadcastChannel` einen Hinweis (`onExternalChange`), damit andere Tabs neu laden, bevor der Nutzer weiterarbeitet. Der Hinweis ist eine Beschleunigung, keine Garantie; die Revisionsprüfung bleibt die Absicherung.
3. Will ein neuerer Build das Schema ändern, schließt der alte Tab seine Verbindung (`onVersionChange`), statt das Upgrade zu blockieren. Ein älterer Build verweigert mit `NewerSchemaError` den Zugriff auf ein neueres Schema (PR #76).

Die verständliche Konflikt-UI entsteht mit dem ersten Editor (v0.4); der Datenvertrag dafür steht.

## Migration und Recovery

- IndexedDB führt ein Schema-Upgrade in einer einzigen `versionchange`-Transaktion aus. Wirft das Upgrade oder wird der Tab geschlossen, bleibt die vorherige Version vollständig erhalten. Beides ist im echten Chromium nachgewiesen; im Unterbrechungstest läuft die Transaktion nachweislich noch, als der Tab geschlossen wird.
- Ein eigener Startup-Recovery-Marker ist dadurch für Migrationen innerhalb einer Datenbank nicht nötig. Er wird erst relevant, wenn ein Ablauf mehrere Datenbanken oder Dateien umfasst.
- `migrateWithBackup` exportiert vor jedem Upgrade im geprüften Backupformat und legt die Kopie in `<name>__backups` ab. Kann das Backup nicht geschrieben werden, startet das Upgrade nicht. Die Kopie deckt ab, was die Transaktion nicht abdeckt: Fehler in einem technisch erfolgreichen Upgrade und spätere Beschädigung.

## Messungen (headless Chromium, Linux, 2026-09-27)

| Messung | Wert |
|---|---|
| Fixture | 100 Aggregate × 5 Revisionen = 500 Commits mit Audit-Event |
| Schreibdauer | 830–950 ms gesamt, also etwa 2 ms pro atomarem Commit |
| IndexedDB-Belegung laut `estimate()` | +180 KiB |
| Backupgröße derselben Daten | 341 KiB (Limit 10 MiB) |
| Quota laut `estimate()` | etwa 0,9 GB (browser- und gerätabhängig) |
| `persisted()` / `persist()` | `false` / `false` |
| Adapter-Bundle inklusive Dexie | etwa 38 KiB gzip |

`persist()` wird von Chromium nach Nutzungssignalen vergeben (zum Beispiel installierte PWA, Lesezeichen, Interaktion); in einem frischen headless Profil wird es abgelehnt. Das bestätigt die Folgerung aus DEC-009: Persistenz darf nicht vorausgesetzt werden, Backup und Restore sind P0, und die App muss den Status ehrlich anzeigen.

## Edge-Nachweis (2026-09-28)

Microsoft Edge 154.0.4258.37 unter Windows 11, gesteuert über Playwright mit dem installierten Edge statt des mitgelieferten Chromium: `PLAYWRIGHT_CHROMIUM_EXECUTABLE="C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe" pnpm exec playwright test --workers 2` (nach `pnpm build`), die bestehende Konfiguration liest diese Variable schon.

- `persistence.spec.ts` komplett grün, also Tab-Koordination mit Revisionskonflikt, Zustand nach Tab-Schließen, abgebrochenes und fehlgeschlagenes Upgrade mit wiederherstellbarem Backup (zusammen mit den übrigen Specs 17/17).
- `persist()` → `false`, `persisted()` → `false`, sowohl headless als auch mit sichtbarem Fenster in einem frischen Profil; `estimate()`-Quota 10 240 MiB. Edge verhält sich damit wie Chromium: Persistenz darf nicht vorausgesetzt werden, Backup/Restore bleibt P0 (DEC-009 bestätigt).
- Nicht geprüft: `persist()` in einer *installierten* PWA mit echten Nutzungssignalen. Das ändert die Folgerung nicht, weil die App ohnehin mit abgelehnter Persistenz umgehen muss.

## Noch offen

- Endgültige Object Stores und Indizes entstehen mit dem ersten echten Aggregat; der Spike-Schema-Stand bleibt experimentell.
- Bestätigter destruktiver Restore und `.dndim`-Bundleformat folgen mit dem Export-/Import-Slice.
